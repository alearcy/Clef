# Choose components without outsourcing engine ownership

**T01 extended evaluation — 2026-11-16.** [Specification](../docs/specs/T01-engine-foundation.md) · [T02 validation draft](../docs/specs/T02-engine-validation.md).

**A Clef-owned core assembled from focused libraries is a reasonable next validation hypothesis, but it is not yet demonstrably cheaper or safer than adapting Maolan.** The concrete shortlist is CPAL for output, Clack for CLAP, and either vst3-rs or a narrow SDK-backed native bridge for VST3; add a bounded queue, hardware MIDI and WAV writing only where the agreed prototype requires them. VST3 and CLAP are joint first priorities, without a fixed order between them; AU follows later. Rust is preferred, not mandatory where native code provides a concrete advantage. Deeper inspection changes the original recommendation: Maolan's helper does not supply the missing native macOS VST3/CLAP editors, and truce-rack has critical host omissions. Neither offers a shortcut around the first hosting gate. **Validate complete hosting before committing to a new engine**, while retaining Maolan as the reuse baseline for the graph, PDC, streaming and lifecycle work Clef would otherwise own.

This is source-based selection research, not dependency adoption or prototype implementation. No builds, local tests, GUI sessions, listening checks or hardware measurements were run. Configured upstream CI and consumer manifests are evidence of engineering activity, not proof that Clef's selected plugins work.

CPAL has multi-platform and sanitizer workflow configurations; rtrb includes Miri, Tree Borrows and ThreadSanitizer checks; midir 0.11.1 includes a CoreMIDI truncated-packet safety fix. These are relevant maintenance facts, not guarantees. Rodio independently consumes CPAL, hound, Symphonia, rtrb and rubato, but several pinned versions are older than the proposed ones. CamillaDSP likewise does not validate rubato 5.1 merely by using an earlier major version. Several projects concentrate maintenance around a small number of contributors; plan to own regression checks rather than infer abandonment or reliability from activity counts. ([CPAL CI](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/.github/workflows/platforms.yml), [rtrb CI](https://github.com/mgeier/rtrb/blob/5596032eda8043c5180ba05d9863e375f0890fbc/.github/workflows/main.yml), [midir changelog](https://github.com/Boddlnagg/midir/blob/db32c3f4fa017d7145395bf04d220625d2733305/CHANGELOG.md), [Rodio manifest](https://github.com/RustAudio/rodio/blob/685e05765c2aff8fbb51e32cda5b18428d09ffbe/Cargo.toml))

**CPAL 0.18.2 is preferable to writing CoreAudio immediately for an output-first instrument proof.** It exposes device/rate/buffer selection and capture/playback timing, and preserves a cross-platform direction. Its macOS minimum is 14.2, so the user's actual deployment target must be checked. Requested buffer sizes are not immutable callback bounds; handle variable callbacks with pre-established storage, and keep querying/control methods that can lock outside the audio callback. Reported playback timestamps include latency estimates, not physical loopback measurements. ([Stable requirements](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/README.md), [Buffer contract](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/src/lib.rs#L330-L355), [CoreAudio timing](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/src/host/coreaudio/macos/device.rs#L910-L930))

Recording/monitoring can change that choice. Stable CPAL has separate input/output builders; inspected **unreleased 0.19 HEAD does not establish synchronized CoreAudio duplex either**. Separate devices introduce clock drift that a queue alone cannot correct. A narrow native CoreAudio backend becomes justified if agreed duplex/recovery requirements expose a concrete limitation; no such backend was audited or measured here. Device errors still require Clef's stop/rebuild/reconnection policy. ([Stable stream API](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/src/traits.rs), [Unreleased capability default](https://github.com/RustAudio/cpal/blob/40ff3adea81757326debba6b2befb747a6699d50/src/traits.rs#L182-L189), [Recovery paths](https://github.com/RustAudio/cpal/blob/e1612d5d98152f8dc2a62e1b51ef7cbf4f7f26b7/src/host/coreaudio/macos/mod.rs#L133-L210))

midir supplies input timestamps whose public origin is connection-relative/unspecified; Clef must map events into sample positions and define late-event behavior. Its CoreMIDI SysEx path can grow storage. rtrb is single-producer/single-consumer: multiple MIDI callbacks and GUI producers require a real topology, with bounded payloads, note-off preservation and off-thread reclamation. For WAV, hound's published 3.5.1 uses 32-bit counters without an intentional pre-overflow size error. A checked wide byte count, complete frames and explicit error-reporting `finalize()` are required for the bounded proof; unreleased HEAD saturation does not make oversized RIFF valid. ([midir input contract](https://github.com/Boddlnagg/midir/blob/db32c3f4fa017d7145395bf04d220625d2733305/src/common.rs#L100-L120), [rtrb ownership](https://github.com/mgeier/rtrb/blob/5596032eda8043c5180ba05d9863e375f0890fbc/src/lib.rs#L322-L356), [hound stable counters](https://github.com/ruuda/hound/blob/2cddb275183a6146c0dff2c758ff936d00147af1/src/write.rs#L429-L436), [Finalization](https://github.com/ruuda/hound/blob/2cddb275183a6146c0dff2c758ff936d00147af1/src/write.rs#L510-L548))

## VST3 and CLAP require a real host service layer

Clack's strongest evidence is focused: lifecycle/thread wrappers, Cocoa NSView handles, GUI/state/port/latency/tail/render extensions, tests for loading/destruction/reentrancy, and configured cross-platform CI/Miri. Version 0.2 addresses prior reentrant-call undefined behavior; that is a reason to inspect the version, not declare it free of defects. Its example ignores `request_restart`; its buffer helpers can grow if capacities are exceeded. Clef must implement the restart state machine, main-thread callbacks, native window lifetime, bounded events and port policy rather than copy the example unchanged. ([Host tests](https://github.com/prokopyl/clack/tree/27ca28391b57a61bad4bb5099288a7bf9247350d/host/tests), [v0.2 release](https://github.com/prokopyl/clack/releases/tag/v0.2), [Example restart placeholder](https://github.com/prokopyl/clack/blob/27ca28391b57a61bad4bb5099288a7bf9247350d/host/examples/cpal/src/host.rs#L99), [Window ownership](https://github.com/prokopyl/clack/blob/27ca28391b57a61bad4bb5099288a7bf9247350d/extensions/src/gui/window.rs#L100), [Event-buffer growth](https://github.com/prokopyl/clack/blob/27ca28391b57a61bad4bb5099288a7bf9247350d/common/src/events/io/buffer.rs#L47))

For VST3, vst3-rs provides generated unsafe bindings and COM ownership helpers, with CI checking examples, tests and regenerated bindings. It leaves module/controller setup, buses, event/parameter queues, state, transport and host callbacks to Clef. The native SDK supplies reusable `HostApplication`, messages/attributes, platform module loaders, `PlugProvider`, event/parameter lists and associated tests. **A narrow SDK bridge can therefore reduce specific reimplementation**, rather than merely substitute C++ for Rust. SDK 3.8.1's inspected public submodule is `586dc5e6c8012c3e4b01c79389375cbe96bdb1da`; its interfaces are `4f547e8e102b47de4a8b8aaf343c73b700786372`. ([Bindings contract](https://github.com/coupler-rs/vst3-rs/blob/b2a45f2d40e602eff5a224b41613735388868590/README.md), [SDK host classes](https://github.com/steinbergmedia/vst3_public_sdk/blob/586dc5e6c8012c3e4b01c79389375cbe96bdb1da/source/vst/hosting/hostclasses.cpp), [PlugProvider](https://github.com/steinbergmedia/vst3_public_sdk/blob/586dc5e6c8012c3e4b01c79389375cbe96bdb1da/source/vst/hosting/plugprovider.cpp#L126), [Hosting tests](https://github.com/steinbergmedia/vst3_public_sdk/tree/586dc5e6c8012c3e4b01c79389375cbe96bdb1da/source/vst/hosting/test))

Neither SDK sample is a turnkey host. Editorhost leaves edit/restart callbacks unimplemented; audiohost hardcodes realtime setup. Its macOS window/IPlugFrame code is useful, but its NSApplication loop must not compete with egui's loop. Official VST3 latency/I/O changes require deactivation, reconfiguration and reactivation; rereading a number during process is insufficient. Switching offline mode likewise requires correct `setupProcessing`. A bridge should encapsulate native objects behind a bounded ABI and caller-owned buffers; it should not own a second device callback, graph or timeline. ([Sample callback stubs](https://github.com/steinbergmedia/vst3_public_sdk/blob/586dc5e6c8012c3e4b01c79389375cbe96bdb1da/samples/vst-hosting/editorhost/source/editorhost.cpp#L94), [Native editor window](https://github.com/steinbergmedia/vst3_public_sdk/blob/586dc5e6c8012c3e4b01c79389375cbe96bdb1da/samples/vst-hosting/editorhost/source/platform/mac/window.mm#L139), [Restart contract](https://github.com/steinbergmedia/vst3_pluginterfaces/blob/4f547e8e102b47de4a8b8aaf343c73b700786372/vst/ivsteditcontroller.h#L123), [Processing modes](https://github.com/steinbergmedia/vst3_pluginterfaces/blob/4f547e8e102b47de4a8b8aaf343c73b700786372/vst/ivstaudioprocessor.h#L125))

**Reject truce-rack 1.1.5 as the shortcut suggested for further investigation in the earlier report.** Its CLAP instantiation passes a null `clap_host` with an explicit TODO. VST3 initializes with null context, omits controller state, provides null parameter-change queues and hardcoded realtime mode, and has limited buses/MIDI. Both format paths allocate vectors during processing; no plugin-latency API was located. These source-observed omissions outweigh its feature table and allocation-free contract. This conclusion concerns the inspected revision, not all future releases. ([Null CLAP host](https://github.com/truce-audio/truce-rack/blob/233f56c7788291b2f24e3f2aba3a767330f72cb7/crates/truce-rack-clap/src/lib.rs#L503), [VST3 state/setup](https://github.com/truce-audio/truce-rack/blob/233f56c7788291b2f24e3f2aba3a767330f72cb7/crates/truce-rack-vst3/src/lib.rs#L806), [VST3 process](https://github.com/truce-audio/truce-rack/blob/233f56c7788291b2f24e3f2aba3a767330f72cb7/crates/truce-rack-vst3/src/lib.rs#L1100))

## Maolan saves engine work but still needs macOS hosting work

Engine `7e7694a915fe7f4f6b927363af68af924a2547bb` remains the inspected Maolan baseline. The newly inspected helper **0.1.3 at `19da7755824aca87f43f9a3d32e040bcb7316e5d`** routes VST3 editors through X11, with macOS null-display stubs and a comment that Cocoa parenting is unimplemented. CLAP floating negotiation omits Cocoa and its X11 fallback has the same limitation. Thus engine show/hide IPC does not deliver the required native macOS editors for either first-priority format. The helper also hardcodes VST3 realtime mode and accepts restart flags without handling them; engine transport still writes position zero/120 BPM. These defects require coordinated engine/helper/protocol work. ([VST3 GUI route](https://github.com/maolan/plugin-host/blob/19da7755824aca87f43f9a3d32e040bcb7316e5d/src/vst3_lv2_host.rs#L392-L465), [macOS stubs](https://github.com/maolan/plugin-host/blob/19da7755824aca87f43f9a3d32e040bcb7316e5d/src/vst3_lv2_host.rs#L172-L185), [CLAP selection](https://github.com/maolan/plugin-host/blob/19da7755824aca87f43f9a3d32e040bcb7316e5d/src/host.rs#L404-L450), [Restart placeholder](https://github.com/maolan/plugin-host/blob/19da7755824aca87f43f9a3d32e040bcb7316e5d/src/vst3/interfaces.rs#L352-L354), [Transport](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/vst3_proc.rs#L430-L439))

Maolan still saves substantial work: ordered plans, compensation at graph sums, MIDI merge/note cleanup, disk streaming, shared live/offline execution and a separate plugin process/watchdog. Both engine/helper are BSD-2-Clause with configured multi-platform CI. Remaining locks, helper waits and allocation paths prevent an unqualified real-time-safety claim. A fork also owns version compatibility, regression checks and upstream merge costs; narrow upstream fixes can reduce divergence but their acceptance is not assured. ([Plan ownership](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plan/render_plan.rs#L1-L44), [Join PDC](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/workers/worker.rs#L1173-L1197), [MIDI cleanup](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/track/process.rs#L618-L664), [Inline locking](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plan/inline_render.rs#L291-L430), [Helper license](https://github.com/maolan/plugin-host/blob/19da7755824aca87f43f9a3d32e040bcb7316e5d/LICENSE))

| Invariant | What Maolan already owns | What a Clef-owned core must implement |
| --- | --- | --- |
| Graph and PDC | Compiler, ordering checks, per-join delays | Valid channels/dependencies, explicit cycle policy, cumulative latency at every arbitrary join including sidechains; coherent updates |
| Real-time handoff | Plan publication/reclamation infrastructure, with remaining locks/allocations | Off-thread preparation/destruction, bounded events, overflow recovery, preallocated processing and latency transitions |
| Timeline/MIDI | Sample-based events and existing note cleanup | Clock mapping, block offsets, tempo context, same-sample ordering, note ownership across stop/seek/loop/remove |
| Live/offline | Shared plan execution and streaming/bounce infrastructure | One processing core with separate drivers, correct plugin modes, latency trimming, tails, cancellation and error handling |
| Hosting/failure | Helper protocol and process boundary, incomplete macOS backends | Lifecycle/buses/state/editor/restart services; an explicit isolation model, with IPC/watchdog/packaging if selected |

Native arpeggiators and M/S encoders/decoders are MIDI/audio processing tools, **not an internal plugin suite**. Maolan's public task variants explicitly enumerate tracks/folders/plugin formats and lack a generic native-processor registration seam. Adding native nodes coherently reaches graph, dispatch and persistence; forcing them through external-plugin IPC is not automatically simpler. A Clef-owned core gives direct placement/ownership but still needs reset, channel, state and latency contracts. This comparison does not select their behavior or authorize implementing them. ([Maolan task types](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/message.rs#L473-L494))

## T02 should discriminate between ownership paths

The current recommendation is conditional: **test the Clef-owned path with Clack plus a deliberate VST3 backend choice before building a general engine**. Rust bindings are a valid hypothesis, not an assumed cost winner; compare the concrete SDK services above before committing to reimplement them. Keep Maolan's graph/PDC/streaming ownership as the reference alternative if custom invariants prove more expensive than fixing its host seam. Do not mix two scheduling engines or adopt another application's feature scope. AU can later join the same justified two-format processing boundary without defining AUv3 scope now.

T02 should use actual VST3 and CLAP instruments/effects, native editor resize/reopen, state recreation, non-120 tempo/nonzero position, sample-offset events/automation, unequal-latency reconverging routing and live/offline output. Agree which port/latency restart, multi-output/sidechain, crash/scanner hang, signed deployment and physical MIDI checks belong in the first gate. Set hardware/workload/tolerances before pass/fail criteria. Scheduled events can establish timing without a keyboard; they cannot establish hardware timing. Neither an editor-only example nor one audible note proves the complete path.

These licenses permit useful reuse routes but do not establish a complete distribution decision. In particular, the pinned VST3 SDK/public SDK and vst3-rs interface submodule use MIT; older SDKs must be checked separately. Symphonia's MPL obligations differ from permissive dependencies. No complete transitive inventory, legal compatibility opinion, current issue triage or independent production-compatibility matrix was produced. The original report's Maolan-first ranking is therefore superseded by this conditional ownership comparison, **not by a final adoption decision**. T01 remains pending; T02 remains a planning draft awaiting its remaining interview and specification agreement.
