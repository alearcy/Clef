# Reuse an engine after targeted validation

> **Follow-up correction — 2026-11-16:** The [extended ownership and library evaluation](Engine%20ownership%20and%20library%20selection.md) supersedes this report's Maolan-first validation ranking. Inspection of Maolan's separate helper confirms missing native macOS VST3/CLAP editor paths; inspection of truce-rack 1.1.5 found critical host omissions, so it is no longer a credible shortcut at that revision. The updated recommendation is a conditional Clef-owned validation path compared against Maolan's reusable engine responsibilities, with VST3 and CLAP first and AU later. No foundation has been adopted; the original findings below remain historical evidence at their stated scope.

**T01 evaluation — 2026-11-16.** [Approved specification](../docs/specs/T01-engine-foundation.md).

**Neither candidate currently earns unconditional adoption for Clef's virtual-instrument-first workflow. Maolan is the stronger first candidate for a bounded validation exercise; SoundCraft is a useful alternative and source of reusable components.** Maolan offers a separate engine, graph-based compensation, MIDI/device infrastructure and process-isolated hosting, but its inspected VST3/AU transport and parameter-timing paths need attention. SoundCraft provides substantial Rust DSP/mix/playback code and an existing egui application, but lacks a working hardware MIDI input layer in the inspected source and has material macOS editor and routing limitations. Both implement meaningful plugin delay compensation (PDC) and offline rendering; neither has been demonstrated here to satisfy the user's plugins, latency needs or export requirements. External libraries can fill specific gaps, but are not evidence that an assembled system will work. The recommendation is to retain one engine as the owner of audio scheduling, routing and PDC, validate the priority workflow, and agree on adoption only after reviewing those results.

## Current code supports reuse, with limited reliability evidence

This evaluation inspected Maolan engine **0.4.22 at `7e7694a915fe7f4f6b927363af68af924a2547bb`**, committed November 9, and its application at `1ec0ea0c4072d15d05ce972b12016eb0e954a9ed`. SoundCraft was inspected at **`648ed9db9a0e98cc55643babffac381521a556c8`**, committed November 16, with workspace version 0.20.1. These immutable revisions govern code findings below. ([Maolan revision](https://github.com/maolan/engine/commit/7e7694a915fe7f4f6b927363af68af924a2547bb), [SoundCraft revision](https://github.com/storytold/soundcraft/commit/648ed9db9a0e98cc55643babffac381521a556c8))

Evidence here means **source inspection**, unless explicitly labeled otherwise. Configured upstream tests and observed release activity establish maintenance effort, not local acceptance. No build, automated runtime test, GUI/editor session, listening check or hardware measurement was performed. The separate Maolan host helper was not traced end to end. Some library documentation uses mutable branch URLs and cached published pages; those components require a pinned checkout before selection.

Maolan configures Linux, Windows and macOS CI with tests, linting, dependency auditing and Miri; this review did not verify the latest run or release binaries. Its application depends directly on the separate engine and host helper. SoundCraft has a recent v0.20.1 release and inspected tests covering device configuration, routing and latency, while its README explicitly calls the project **pre-alpha**. Its engine also depends on a broader application model, craft-libs revisions and patched egui/winit forks. Neither project's inspected evidence establishes stable APIs or a broad, independently verified commercial-instrument compatibility record. ([Maolan CI](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/.github/workflows/rust.yml), [Maolan application dependencies](https://github.com/maolan/maolan/blob/1ec0ea0c4072d15d05ce972b12016eb0e954a9ed/Cargo.toml#L27-L29), [SoundCraft release](https://github.com/storytold/soundcraft/releases/tag/v0.20.1), [SoundCraft README](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/README.md), [SoundCraft workspace](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/Cargo.toml))

The following sections substantiate the table and distinguish missing functionality from unverified behavior.

## Hosting gaps directly affect instruments on macOS

Maolan's engine exposes format-specific processors, subprocess scanning, shared-memory processing and a watchdog that marks a failed child for bypass. Those are substantive integration seams, but a compatible `maolan-plugin-host` executable must also be packaged and validated. A floating editor request is not proof of successful editor opening, resizing and teardown. VST3 embedded editor methods return unsupported; CLAP embedded-information methods are also incomplete. ([Scanner](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/mod.rs#L84-L127), [Watchdog](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/watchdog.rs#L1-L24), [VST3 editor methods](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/vst3_proc.rs#L564-L620))

**Maolan sends fixed tempo 120 and playhead zero in the inspected VST3 and AU processing paths.** Its CLAP path supplies transport, but VST3 and CLAP parameter setters ignore the supplied frame offset. These are concrete source findings, not hypothetical compatibility concerns: tempo-synchronized instruments and accurately timed automation cannot rely on those paths unchanged. The smallest responsible work would be at the existing processor/protocol boundary, with tests, before considering wholesale host replacement. ([VST3 processing](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/vst3_proc.rs#L406-L514), [AU processing](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/au_proc.rs#L519-L625), [VST3 parameter timing](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/vst3_proc.rs#L305-L326), [CLAP parameters](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/clap_proc.rs#L506))

SoundCraft has genuine implementations of all three formats, including state handling and instrument events. Its VST3 implementation hosts an NSWindow/NSView editor on macOS, but deactivates auxiliary audio buses, so it does not supply VST3 sidechains. AU covers AUv2 instruments/effects and state but excludes AUv3, Cocoa editor views, extra buses and some parameter scopes. CLAP supports floating editors; embedded-only editors are hosted on Windows, with the equivalent macOS path missing in the inspected contract. Native plugins execute in the application process. ([VST3 host](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/vst3-host/src/lib.rs), [VST3 bus activation](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/vst3-host/src/ffi/instance.rs#L352), [AU host](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/au-host/src/lib.rs), [CLAP host](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/clap-host/src/lib.rs))

SoundCraft's clip scheduler supports sample offsets and controller chase, but fixes events to MIDI channel 1. No device-opening MIDI backend was found in the inspected playback/UI/manifests: `setup.midi_input_devices` stores configuration rather than establishing input connections. This makes live hardware MIDI a required integration for keyboard-based workflows, though the user has not yet specified a particular controller or multitimbral requirement. A library can supply port access; clock conversion, scheduling and note ownership still belong in the engine. ([Clip MIDI](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/src/midi.rs#L17), [MIDI setup command](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/engine/src/cmd/setup_more.rs#L459), [Playback dependencies](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/playback/Cargo.toml))

Current source also corrects stale documentation: SoundCraft implements VST3 `IMessage`/`IAttributeList`, selectable audio devices/rates/buffers, and streaming WAV recording. It should not be rejected for the older documented limitations in those areas. ([VST3 host application](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/vst3-host/src/ffi/host.rs#L55), [Devices](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/playback/src/devices.rs), [Recording](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/playback/src/record.rs#L39))

## PDC exists, while deadlines and export correctness remain open

Maolan propagates input plus plugin latency and delays shorter inputs at sum nodes. Plans are built on the control side, atomically published and reclaimed through basedrop. Its routing has cycle checks; compiler feedback recovery is a separate mechanism. This is a stronger general graph starting point than merely adding a fixed master delay. However, changing delay configurations allocates temporary buffers, VST3/AU MIDI-output paths construct vectors, and the inline coordinator still takes several mutexes. The claim that scheduling leaves particular locks uncontended needs proof. ([Sum compensation](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/workers/worker.rs#L1173-L1197), [Delay transitions](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plan/render_plan.rs#L159-L202), [Inline coordinator](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plan/inline_render.rs#L291-L430), [Routing](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/routing.rs))

Maolan also synchronously waits for its helper. The timeout is bounded by `min(100 ms, 2 × device period)` when the period is known, otherwise 100 ms. **That is a timeout ceiling, not measured added latency.** Process isolation protects a different boundary from audio-deadline safety; neither benefit removes the need to measure behavior when a plugin stalls or dies. ([IPC timeout and wait](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/plugins/ipc.rs#L12-L47))

SoundCraft includes instrument and insert latency in strip compensation and adds aux/master latency. Its algorithm uses a global aux maximum, so arbitrary nested joins are not established as correctly compensated by inspection. Aux dependencies receive exact depth ordering for acyclic graphs; cycles fall back to an eight-hop bounded ordering instead of explicit rejection or a defined feedback-delay model. Tests cover basic joins, master latency and long chains, but were not run here. ([Mix compensation](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/src/lib.rs#L347), [Routing and cycle policy](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/src/routing.rs#L37), [Routing tests](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/tests/it/aux_routing_order.rs))

SoundCraft's VST3 host responds to changing plugin latency, but delay rings allocate when a new delay exceeds capacity; equivalent dynamic AU refresh was not found. Session synchronization and configuration changes also allocate from callback-owned code. General Rayon workers and standard mpsc channels require scrutiny under load. Its no-allocation processing contract describes desired steady-state behavior, not a demonstrated bound during editing. ([Delay rings](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/src/strip.rs#L64), [Callback synchronization](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/playback/src/callback.rs#L123), [Workers](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/src/threads.rs#L27))

Both reuse processing infrastructure offline. Maolan renders dependency-closed bounce/stem plans without device pacing, but the inspected loop stops at requested length; plugin-tail discovery, offline-mode negotiation and leading-latency trimming remain unresolved. SoundCraft's `RangeRender` trims latency measured in the first block and its bounce streams through a temporary `.part` file, with a four-hour limit. The requested range does not automatically include reverb tails; its separate clip-FX ten-second tail policy does not establish complete mix-bounce tails. Neither implementation was tested with real-time-only plugins or changing latency during export. ([Maolan bounce](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/workers/worker.rs#L288-L450), [SoundCraft offline renderer](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/mix/src/offline.rs), [SoundCraft bounce](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/engine/src/io.rs#L320))

## External libraries should fill gaps within one processing owner

**Product scope clarification (2026-11-16):** Clef prioritizes robust hosting of external instruments and effects; it does not currently need an internal plugin suite. Native arpeggiators and M/S encoders/decoders are MIDI/audio processing and routing tools, without an assumed insert/send-slot presentation. Assess engine integration points for these responsibilities separately from external plugin hosting. Their placement, order, timing and channel semantics remain to be specified and verified; this report does not establish that either engine already supports the intended workflows. A plugin-authoring framework such as nice-plug is outside the present hosting solution scope.

With Maolan, retain device/MIDI I/O, render scheduling and graph/PDC; Clef supplies its own egui presentation and product behavior. Tokio integration and helper discovery/packaging are explicit costs. With SoundCraft, preferentially reuse DSP/mix/playback/hosting crates rather than importing its entire engine and application scope. Its existing egui work is useful reference evidence, while its craft-libs dependencies and UI forks increase integration maintenance. Neither route requires adopting another DAW's feature backlog. ([Maolan initialization](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/src/lib.rs#L167-L201), [SoundCraft engine manifest](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/crates/engine/Cargo.toml))

For hosting gaps, **Clack is a genuine CLAP host foundation**, with lifecycle/thread ownership and latency extensions, while `vst3` 0.3.0 supplies unsafe bindings rather than a complete host. Clack exposes reported latency and a change callback; the engine must still compute graph compensation. `truce-rack` is a focused multi-format candidate before writing a replacement: its documentation claims AUv2/AUv3/VST3/CLAP processing, events and editors. That claim was not verified through a full format-wrapper audit or real-plugin run, so it is a candidate to inspect, not an already-proven solution. Native AU APIs likewise supply platform services without solving the DAW graph. ([Clack lifecycle](https://docs.rs/clack-host/0.2.0/clack_host/), [Clack latency source](https://raw.githubusercontent.com/prokopyl/clack/main/extensions/src/latency.rs), [VST3 bindings](https://docs.rs/vst3/0.3.0/vst3/), [truce-rack](https://github.com/truce-audio/truce-rack), [Apple AUAudioUnit](https://developer.apple.com/documentation/audiotoolbox/auaudiounit))

CPAL supplies portable audio-device access, midir supplies MIDI ports, and rtrb supplies a bounded single-producer/single-consumer queue. Use an engine's existing fitting implementation first. Adding MIDI input to SoundCraft still requires timestamp conversion and live-event integration; adding a queue still requires overflow and note-off policy. None supplies end-to-end PDC or export correctness. A second independent graph, transport clock or device callback would increase ownership conflicts rather than complete the first engine. ([CPAL](https://github.com/RustAudio/cpal), [midir 0.11.1](https://docs.rs/midir/0.11.1/midir/), [rtrb 0.4.1](https://docs.rs/rtrb/0.4.1/rtrb/))

Licensing does not exclude either engine at the top level: Maolan is BSD-2-Clause; SoundCraft declares MIT OR Apache-2.0, with separate asset/font and branding notices. Clack declares MIT OR Apache-2.0. A complete chosen dependency/helper inventory remains necessary. Two current facts deserve version precision: the inspected VST3 SDK license at `3cdf9ca5d1f5b1b21e0a86832aa4abe55607bd96` is MIT; JUCE at `d60b7a78030661574a615b586d9325ba7a7fa7dd` offers AGPLv3 or a commercial JUCE 9 license. Those texts do not determine older pinned SDKs or every bundled module's obligations. JUCE's host API is a fallback to assess only if Rust options fail; its C++ bridge, message loop and licensing cost need a separate explicit decision, with no CLAP support established here. ([Maolan license](https://github.com/maolan/engine/blob/7e7694a915fe7f4f6b927363af68af924a2547bb/LICENSE), [SoundCraft notices](https://github.com/storytold/soundcraft/blob/648ed9db9a0e98cc55643babffac381521a556c8/NOTICE), [Clack manifest](https://raw.githubusercontent.com/prokopyl/clack/main/host/Cargo.toml), [VST3 SDK license](https://github.com/steinbergmedia/vst3sdk/blob/3cdf9ca5d1f5b1b21e0a86832aa4abe55607bd96/LICENSE.txt), [JUCE license](https://github.com/juce-framework/JUCE/blob/d60b7a78030661574a615b586d9325ba7a7fa7dd/LICENSE.md), [JUCE host API](https://docs.juce.com/master/classjuce_1_1AudioPluginFormatManager.html))

## Agree on a narrow gate before committing the foundation

The ranking is an engineering judgment from the inspected architecture: **validate Maolan first** because a separate reusable engine, graph-level PDC, MIDI infrastructure and process boundary fit Clef's priorities. Its transport/timing defects are explicit blockers to address or disqualify, not details to defer after adoption. SoundCraft remains the alternative if Maolan's helper/editor/deadline costs prove worse than adding MIDI and completing macOS hosts in SoundCraft. Neither earns the label “proven” from this research alone.

A proposed gate should cover one agreed instrument and latency-reporting effect for each initially required format, native editor lifecycle, state restoration, non-120-BPM transport and event timing. It should include live MIDI only once the user confirms that workflow, plus a compensated parallel/nested route, latency changes, an invalid routing attempt, and live/offline output alignment with a tail. Device changes, plugin stalls/crashes and edit-time underruns should be observed on the intended macOS hardware. These are proposed checks, not tests already performed or a newly authorized implementation phase. The plugin set, workload, latency tolerance, channel/bus requirements and format delivery order must be agreed before defining pass/fail thresholds.

**Decision pending:** agree whether Maolan should enter that bounded validation stage, or select a different path after reviewing these tradeoffs. DSP, hosting and engine adoption remain open; no dependency has been added. T01 remains incomplete until the user agrees on the foundation and the decision is recorded. Graphify generation remains pending because Clef contains no application source.
